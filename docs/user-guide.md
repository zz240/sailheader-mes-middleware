# 边缘网关操作手册

> 面向实施工程师：按下面的顺序配置一个真实同步任务。
> 通用流程：**先建数据源 → 再建任务和动作 → 启用并执行 → 出问题看消息历史**。
> 术语定义见仓库根 `CONTEXT.md`；本文档随功能变更同步更新。

## 0. 本地环境

依赖：Docker（MySQL + RabbitMQ）、JDK 21、Node 22。启动方式见 README「快速运行」。

- 队列发消息（联调）：`tools/mq-publish.ps1 -Queue <队列名> -PayloadFile <json文件>`
- 本地 HTTP mock（9099，模拟客户 ERP）：`node tools/mock-9099.cjs`，请求日志在 `%TEMP%\edge-mock\bom-mock.log`

## 1. 数据源

数据源 = **连接实例**（地址 + 鉴权），不绑定具体表/队列/接口路径（那些在动作里配）。

操作步骤：

1. 打开「数据源」页，点「新建数据源」；
2. 填：名称、站点 ID、类型（HTTP / MySQL / RabbitMQ）、地址；
3. 按类型填 `addition`（JSON）：
   - **HTTP**：地址填根地址（如 `http://localhost:9099`）；addition 填 `{"token":"..."}`（可选，Bearer 鉴权）
   - **MySQL**：地址填 `jdbc:mysql://host:3306/库名`；addition 必填 `{"url":"jdbc:...","username":"...","password":"..."}`
   - **RabbitMQ**：地址填 `amqp://host:5672`（或 `host:5672`）；addition 可填 `{"host":"...","port":5672,"username":"guest","password":"guest"}`（有默认值）
4. 保存后可用「测试连通性」验证；「结构探测」输入表名或样例 JSON 查看字段列表（供后续映射用）。

## 2. 任务

操作步骤：

1. 打开「任务」页，点「新建任务」；
2. 填：名称、站点（下拉）、**方向**（北向=客户→MES，南向=MES→客户；只是业务标签）、**调度**（不自动 / 每 N 分钟 / 每 N 小时 / 每天 HH:MM / 每周（周几）+ HH:MM；`不自动` 仅保留手动/外部/重投触发）、重试次数、退避毫秒；
3. 保存后任务默认停用，点「启用」才注册路由。

常用操作：启停（「停用/启用」）、手动执行（「执行」，会立刻跑一次）、删除。

> 任务列表的「最近状态 / 最近时间」是**最近一次运行**的结果：手动执行、自动调度、MQ 消费与断点重投都会更新
> （失败时「最近错误」显示该次运行的根因）。

> 注意：动作变更后路由会自动重建；若任务处于“启用但无消费者”的异常态，先停用再启用一次。

## 3. 动作（动作链）

点任务行的「动作」进入动作链，点「添加动作」。填：名称、类型、序号（执行顺序）。按类型填各自字段：

| 类型 | 必填字段 | 说明 |
|---|---|---|
| READ_SQL | 数据源（MySQL）、SQL、水位策略、水位列、批大小 | 增量/刷量读取；SQL 里可用 `{watermark}` 占位，`batchSize`（缺省 500）控制每批行数 |
| WRITE_UPSERT | 数据源（MySQL）、表名、幂等键 | 按业务主键 upsert |
| HTTP_CALL | 数据源（HTTP）、路径、方法 | 地址取数据源根地址 + 路径；**响应进链上上下文**（本动作序号），后续 FIELD_MAP 可用 `sourceStep=本动作序号` 取响应字段（如 `results[0].handle`）；出站后消息体仍是本次请求体（#123/#126） |
| MQ_CONSUME | 数据源（RabbitMQ）、队列 | **只能作为链首（序号 1）**；exchange/routingKey 可选 |
| MQ_PUBLISH | 数据源（RabbitMQ）、exchange、routingKey/queue、body 步骤 | 发消息通知 |
| FIELD_MAP | 映射规则（在「编辑映射」的全屏编辑器里配，弹窗里只有一句提示） | 字段映射 |
| ONE_TO_MANY | **档位**（拆分 / 还原）+ 来源步骤 / 来源路径；拆分档还要「元素键」，还原档要「响应配对字段」与「结果落进 body 的键」 | **一分多**（1 → N），两档：**拆分** = 把一份报文里的数组摊成 N 条消息（每元素一条），此后每个动作逐条执行——来源步骤留空 = 拆当前消息体；来源路径留空 = 来源本身就得是数组；「保留外层字段」开着时父消息的字段会摊平进子消息（头行 + 子行那种形态）。**还原** = 把出站拿回来的响应按配对字段摊回**原来那几条消息**，消息身份与批号都沿用（不新造消息）——来源步骤通常填出站那一步的序号；没有响应的出口（MQ 发布）不摆这一档；响应里有一条配不上就整批失败。还原档还要求链上**上游有合并动作** |
| AGGREGATE | 请求体字段名 | **合并**：把走到它这里的一批消息攒齐、打成一条报文 `{"<字段名>": [ … 每条消息自己那一片 … ]}`（N → 1）。**它自己不发请求**——发去哪儿由链上**后面**的 `HTTP_CALL` / `MQ_PUBLISH` 决定（打包完链上只有一条消息，出站动作因此天然只发一次）。攒齐的边界 = 上游读取批读完那一刻，**没有**条数 / 超时参数：要限制「一次请求几条」就调读库那一步的批大小 |

约束：一条任务最多一个 MQ_CONSUME、最多一个带水位的 READ_SQL。保存后「校验任务」可看配置问题。

基数变化那两类动作（**一分多** `ONE_TO_MANY` 的两档 + **合并** `AGGREGATE`）怎么搭配成一条批量链，见下一节。

## 4. 批量接口怎么做（一次请求 N 条 / 一份报文拆成多行）

先认形状，再配链。三种形状与做法：

**① 对端要「一次请求 N 条」（批量接口）**：读一批 → 合并打包 → 出站一次 → 还原

1. `READ_SQL`：**读库那一步的批大小就是「一次请求几条」**（如 20 或 1000）——这是唯一的条数旋钮；
2. `AGGREGATE`：只填「请求体字段名」（对端要的数组字段名，如 `codes`）。它只打包、不发请求，
   排在它**后面**的才是出站动作；
3. `HTTP_CALL`：填对端批量接口的路径。打包完链上只有一条消息，所以这一次请求天然只发一次；
4. `ONE_TO_MANY`（**档位 = 还原**）：来源步骤 = 出站那一步的序号；响应配对字段 = 对端在每一项里回的业务键（如 `code`）；
   结果落进 body 的键 = 你要往下用的那一份（如 `handle`）；
5. 之后每个动作逐条执行（如 `WRITE_UPSERT` 按 `FCode` 把 `FHandle` 回写进库）。

要发给两个终端，就在链上摆两个出站动作：顺序执行（前一个失败，后面的不发），每个出站动作各自一个「重发这一批（N 条）」。

**② 一份报文要拆成「头一行 + 子 N 行」**：`ONE_TO_MANY`（**档位 = 拆分**）

来源是那份报文（「来源步骤」留空 = 当前消息体），「来源路径」指向子件数组（如 `lines`），
「元素键」填子件里的业务键字段（如 `FSeq`）；「保留外层字段」开着时父消息的表头字段会摊平进每条子消息。
拆分之后每个动作逐条执行（头行由链上另一个动作、或另一条任务负责写）。

**③ 源库里就是明细表，只是对端要整份报文**：读侧聚合，不用改配置

在 `READ_SQL` 的 SQL 里用 `JSON_ARRAYAGG`（MySQL）/ `FOR JSON PATH`（SQL Server）把明细折成一列字符串，
映射里用 `$parse` 把它还原成数组——「一单多行 → 一条报文」的现成做法（影子站点的 A2 / A7 那条链就是这么跑的，
见 `tools/shadow-site/README.md`）。这时水位要落在**明细级**自增列上（拿头级水位会在批边界漏单）。

> **快照容量限制（不是缺陷）**：一批打出来的报文装不下快照列
> （`message_step.data_snapshot` / `input_snapshot` 与 `job_run.input_snapshot`，`MEDIUMTEXT` = **16 MB**）时，
> 那个动作**显式失败**，历史里不会留半份报文。怎么绕：**把读库那一步的批大小调小**（唯一有效的旋钮），
> 或缩小每条消息的字段。别指望「超了就截断存一份」——半截报文会让断点重投在解析处报一个离现场很远的错
> （ADR-0015 / ADR-0017 决策 8）。真机上 1000 条码的批量报文约 80 KB，离这条线还很远。

## 5. 字段映射

字段映射在动作表上的**「编辑映射」**里配（全屏编辑器，每个目标字段一行）。推荐流程：

1. **打开**：任务 → 动作 → 动作表上 FIELD_MAP 那一行点「编辑映射」（新建 FIELD_MAP 时在动作弹窗里点「去配字段映射」，同一个编辑器）；
2. **来源**：编辑器左边是来源字段清单（链上更早那个动作最近一次成功运行的输出），点一项就填进当前行，不用手打路径；顶部「默认来源」可换一个更早的动作；
3. **目标**：编辑器打开时按写目标动作那张表**探出来的目标字段**铺行；探不出来（写目标是 HTTP / MQ）就自己加行、手输目标字段路径；
4. **数组映射**：数组字段占一行，在这一行上选**来源数组**，下面展开子行——子行的目标字段与来源都写相对路径；要取数组外层的表头字段就从左边清单的「外层」分组里点；
5. **转换**：点行里的转换就地改（直接映射 / 数字转换 / 日期格式化 / 枚举映射 / 常量 / 拼接 / 行号），参数在行里编辑，不开弹窗；
6. 点「校验配置」看有没有问题（错在哪一行、编译出来的 JSONata 与规则 JSON），改完再点一次，然后保存。

高级：深层数组的任意重排走编辑器顶部的「高级：手写 JSONata」——那是 `mode:EXPRESSION`，直接写一整段表达式（逃生通道，常规场景不需要）。

## 6. 消息历史与断点重投

任务执行会记录为**运行（job_run）+ 消息步（message_step）**，成功与失败全程可见：

1. 打开「消息历史」页（默认查 FAILED，可按任务过滤、按业务键检索、分页）；
2. 「消息步」看每条消息穿过每个动作的结果（动作名/状态/数据/错误），可按运行/消息/业务键分组；
3. 修复原因（如目标服务恢复）后，对一条 `FAILED` 消息步点「重投」——系统用**该步数据**从该动作**精确断点续跑**，成功后该消息步状态变 `REDELIVERED`。
   重投会一并带上**更早步骤的输出**：下游字段映射引用上游步骤（`sourceStep`）时，映射结果与首次执行一致，不会静默变空。
   依赖**没修好**时重投会直接报错（`重投失败：<原因>`），该消息步**保持 `FAILED`**、可以再投一次——看到 `REDELIVERED` 才代表目标端真的收到了。
   「尝试次数」列是该步的**总尝试次数**（含任务配置的自动重试）：`1` = 一次就成功，`3` = 试了 3 次才成（或 3 次都失败）。

> 合并过的链上，出站那一步那一批的组头上还有一个「重发这一批（N 条）」：**一次点击 = 一次请求**——从摘要行
> （整批报文只存这一份）取回整份报文再发一次，新运行里摘要行与这一批每条各记一行。合并**之前**的步骤仍是
> 上面那种逐条重投。**这不是 bug**：合并那一步的输入就是整批报文，摆 N 个「重投这一条」等于点 N 次发 N 遍。

> 旧 `dead_letter` 已弃用（无迁移）；新数据从 `job_run`/`message_step` 开始累积。

## 7. 模板

「模板」页：新建模板填名称 + `configJson`（`{"job":{...},"actions":[...]}`），支持导出/导入/版本管理，用于把固定部分沉淀复用。

## 8. 站点与外部触发

「站点」页：站点名称、时区、建议器覆盖；可生成 **API Key（仅显示一次，妥善保存）**。

外部系统触发任务：

```powershell
curl -X POST http://<网关地址>:8080/api/external/jobs/<任务ID>/trigger `
  -H "X-API-Key: <站点APIKey>" -H "Content-Type: application/json" `
  -d '{"字段":"值"}'
```

## 9. 常见问题

- 消息“消失”但任务显示成功：检查 HTTP_CALL 动作的数据源是不是指向了网关自己（SPA 兜底会返回 200），目标应是真实接口或 mock；
- 队列收不到：确认 MQ_CONSUME 的队列名与发布方一致，任务已启用；
- 消息步重投失败：任务未启用、该步初始输入不是 JSON，或**依赖仍未恢复**（返回 `重投失败：<根因>`，消息步保持 `FAILED`——修好再投一次即可）；
- 配了合并、目标端却收到 N 次请求：检查出站动作（`HTTP_CALL` / `MQ_PUBLISH`）有没有排在 `AGGREGATE` **后面**——排在前面就是逐条发；
- 批量动作失败、错误说报文装不下：把**读库那一步的批大小**调小（见 §4 的「快照容量限制」）；
- 单独重投一条批量数据、对端只收到 1 条：这是有意的——它自己形成一个只有一条的上游批，立刻发，不挂在那里等（ADR-0017 决策 5）。
