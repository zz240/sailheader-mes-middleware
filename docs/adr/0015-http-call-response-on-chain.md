# ADR-0015: HTTP_CALL 把响应当作本动作的输出放上链

- 状态：已接受
- 日期：2026-09-20
- 相关：#123（响应回链）、#126（响应顶替消息体）、#127（快照列容量）、ADR-0002（南北向通信）、ADR-0003（失败即停）、ADR-0009（消息历史）

## 背景

`docs/action-chain-design.md` §2 早就定了契约：**每个动作完成后写 `context[actionIndex] = 输出`**。
`HTTP_CALL` 一直没有兑现——它只出站，响应留在 `Exchange` 的 body 上，既不进 `context`，也没人拦着它。

这一处缺口同时长出两个现场问题（影子站点真机验收刨出来的）：

1. **响应不可寻址（#123）**。紧跟其后的 `FIELD_MAP` 想用 `sourceStep = <HTTP 序号>` 取响应字段取不到；
   B6「标识服务注册 → 拿 `handle` 回写 `MDM_Code.FHandle`」这类对接直接做不了，只能另建一条回传链。
2. **响应静默顶替消息体（#126）**。Camel HTTP 组件默认把响应装进 body，于是链上"当前数据"被换掉：
   响应为空（204 / 空 200）时 body 变 `null`，紧随的 `WRITE_UPSERT` 对 `null` 取 `keySet` 直接 NPE，
   一次**成功**的调用被判成整链失败。影子站点 B1 链首次 86/86 全失败，唯一绕法是调换动作顺序。

两条是同一处改动的两个面：只做一面都会留下排序陷阱。

## 决策

1. **恒捕获，不加开关**。`HTTP_CALL` 出站后把响应解析进 `edge.context[本动作序号]`：
   JSON 对象 → `Map`、数组 → `List`、标量 → 对应 Java 值、**非 JSON 文本 → 原样字符串**、空响应体 → `null`。
   不新增 `captureResponse` 之类的配置项，也不新增动作种类——契约本就要求每个动作都写 `context`，
   HTTP 动作的输出就是响应。前端因此不需要新表单。
2. **消息体还原为本次请求体**。出站后链上 body 保持为动作开始时的 body（即 `input_snapshot`）。
   想继续往下传响应，就显式引用该动作序号（下一步 `FIELD_MAP.sourceStep`，或后续动作的取源参数）。
3. **失败面不变**。目标端 4xx/5xx 时 Camel HTTP 组件抛 `HttpOperationFailedException`，根本走不到捕获那一步：
   不写 `context`、不执行后续写回，按 ADR-0003 失败即停 + 重试退避。
4. **捕获内容不截断**。响应大小由目标端决定，本地拦不住：装不下 `message_step` 快照列时，
   该动作**显式失败并给出可读错误**（指出哪一步、多少字节、容量多少），绝不写半截 JSON——
   写半截的话，断点续投会拿着一个语法都不完整的上游快照去重建 `context`。
   容量值跟着列宽走：**`MEDIUMTEXT` 的 16777215 字节（16 MB）**（#141 起；此前是 `TEXT` 的 65535 字节，
   那个「动作成功却被判失败」正是这次修掉的）。
   **这道闸只给捕获内容**：其余动作的快照（本地数据）行为一概不变，仍由写库报错；容量不再单独放宽，
   跟着列型一起变。
5. **断点续投按 JSON 值还原**。`edge.resumeContext` 从各步 `data_snapshot` 重建时，对象 / 数组 / 标量
   都回填（HTTP 响应可以就是数组）；只有解析不出来的**非 JSON 文本**不进上下文（与一段乱码无从区分），
   且任何情况下都不因此阻断整次重投（#90 的边界，本次只放宽到"任意 JSON 值"）。

## 替代方案（被否）

- **B：新增动作种类（如 `HTTP_REQUEST`）= 请求 + 解析响应合一。**
  否：链上会多出一种与 `HTTP_CALL` 语义重叠的动作，配置界面与校验要多一套；而"响应进 context"
  本来就在已确认的契约里，不是新能力。
- **C：不改产品，MES 侧另建一条回传链。**
  否：每个"调用完要拿对方返回"的对接都要多配一条链，且两条链之间没有共享上下文，
  调用与回写无法在一条消息里对账。
- **`captureResponse` 开关（原票选项 A 的开关形态）。**
  否：契约要求每个动作都写 `context`，给 HTTP 动作开个"可以不写"的口子会让"某个字段取不到"
  变成配置问题，现场无从排查。

## 后果

- `HTTP_CALL` 的 `data_snapshot` 语义不变（input = 请求、data = 响应），历史页无需改；
  新增的是响应**同时**进了链上上下文。
- 想映射响应字段，配置里显式写 `sourceStep = <HTTP 动作序号>`（前端按动作序号选源，已支持）；
- 捕获内容超快照列容量会**让该动作失败**——这是刻意的：宁可失败也不要一份断点续投用不了的半截快照。
  受 #127 容量限制的链（如 A7BIG 那种整份大报文）在 #127 落地前仍按旧路径（写库报错）处理，
  本次没有扩大这道闸的作用范围。
- 断点续投时数组/标量快照的行为变了：以前这类上游步骤不回填（映射静默出空），现在按 JSON 值还原。
