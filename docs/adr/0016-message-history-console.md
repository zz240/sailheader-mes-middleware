# ADR-0016: 消息历史页对齐原型（双栏控制台 + 只读聚合与单步计时）

## 状态

- 相关：ADR-0013（控制台视觉体系与分期，本条是其第 4 期）、ADR-0009（消息历史与可靠性）、
  ADR-0003（失败即停 / 重试 / 死信）、ADR-0015（HTTP_CALL 响应回链）、
  `frontend/prototype/README.md`、`CONTEXT.md`（快照对照 / 动作耗时两条术语）
- 实现：规格 = **#128**（`ready-for-agent`）；票 = **#129–#137**（九张，阻塞边用 GitHub 原生依赖，
  前沿是 #129）；设计稿入库 = `frontend/prototype/04-message-history.html`
- 取代：无。本条**不修订** ADR-0013 的令牌口径与分期结论，只把「消息历史页的结构对齐」从它的
  「已知不做」里摘出来单独成契约

## 背景

ADR-0013 把控制台统一到原型那套视觉体系，分三期落地，并明确把一件事列为**已知不做**：

> 控制台五个页面的**信息密度重排**（消息历史 25 列、任务页 32 个表单项）不在本期范围……
> **真要做需另开设计**。

现在设计来了：2026-09-20 的同一批导出里多了一支 `message-history.html`（87 KB，1346 行，
与 `01/02/03` 同一套令牌、`:root` 逐字一致）。

现状与它差的**不只是外观**。`frontend/src/views/HistoryView.vue`（343 行）是两张 Element Plus
表格（`el-table` 展开行 + `el-collapse` + `el-dialog`）；原型是**全高双栏控制台**：筛选条 →
左列表（运行 / 消息步两个模式）→ 右详情（消息切换 + 步骤链 + 单步卡 + 快照面板 + 「与上一步对照」）、
外加计数条与断点重投弹窗。这是信息架构改造，不是换皮。

两处数据缺口必须先说清，否则票会被写成「纯前端」：

- 原型界面上的四个计数（运行 / 消息 / 消息步 / 失败步）与运行行的 `N 消息 · M 步 · 失败 K`，
  **今天没有接口给**：`/history/runs` 只回分页记录 + `total`。
- **每步耗时**在原型里是三处一等信息（运行行、步骤链每个节点的 `title`、单步卡），而全仓**零计时**：
  `spike/src/main/java` 里没有任何 `currentTimeMillis` / `nanoTime`，`message_step` 也没有这一列。

## 决策

1. **契约归本条，不归 ADR-0013。** 0013 的范围是「令牌层 + 编辑器这棵树」，本条管消息历史页的
   结构与用法。原型入库为 `frontend/prototype/04-message-history.html`，ADR-0013 分期表只加一行指过来。

2. **照抄的是信息架构，控件仍是 Element Plus**（沿用 0013 决策 4：不引新 UI 依赖）。自绘范围
   **限定在组件库没有的那几件**：状态芯片、步骤链、快照面板、对照块。双栏骨架与筛选条用组件库控件搭。

3. **本页全高、页内不滚、栏内滚**（原型 `body{overflow:hidden}` + 栏内各自滚动）。只改本页根节点与
   局部样式，**不动 App 壳**的 padding / 布局——另外四个页面不受影响。代价是本页视觉节奏与它们不同，
   接受：它本来就是控制台型页面，不是表单型页面。

4. **边界沿数据形状切，不沿视觉块切。** `HistoryView.vue` 退成容器（状态 / 取数 / 分页 / 模式 /
   重投编排），拆到 `frontend/src/components/history/`：`HistoryFilters`、`HistoryListPanel`、
   `MessageDetailPanel`、`StepDetailCard`（唯一同时吃「本步 + 上一步」的组件）、`SnapshotPanel`、
   `SnapshotDiff`、`RedeliverDialog`；样式独立成 `styles/history-console.css`，只用 `tokens.css` 的令牌。

5. **语义一个都不改。** 两个模式与它们的默认值原样保留——消息步检索**默认只看 `FAILED`**（#74），
   并按原型把这句话显式写在界面上（现有实现把它藏在 select 的 placeholder 里）；runs 视图的业务键
   筛选命中**该运行下任一条消息**即保留整条运行，且只展示命中的业务键；分页保留（换成原型风格的分页条）；
   「展开运行只取前 100 步」这个隐藏上限**显式化**（给出提示或去掉）。
   运行侧的业务键筛选由 #129 随骨架一起落地；**运行行上「命中的业务键」小标签要等 #130**——
   那需要每运行摘要接口把命中的 key 一并带回来（只筛不显示是这一票的已知缺口）。
   生效口径：任务 / 状态下拉**即时生效**，业务键敲回车或点「查询」；改任何筛选都回到第 1 页。
   **补记（#136 落地时）**：原型 `stepMatches` 里那句 `state.status === 'all' ? 'FAILED' : state.status`
   把「全部状态」也当成 `FAILED`——消息步那一侧因此**没有**「全看」的入口，与 #136 的票面不符。
   按票面落成三档：「没选」= 默认只看 `FAILED`（并把这句写在**列表头、筛选条右端与状态那格的占位**上）、
   明确选「全部状态」= 不带 `status`、选具体状态 = 只看那一个。`businessKey` 与分页口径照旧。
   同一票还给消息步列表按页补上所属运行的 `jobId`（`@TableField(exist = false)` 的**只读投影**，
   `message_step` 表没有这一列）：行上要写「任务 #id」，没有它就只能由界面按行补拉运行——
   正是决策 6 拒绝的 N+1。
   **补记（#131 落地时）**：「展开一条运行只取前 100 个消息步」这个隐藏上限**去掉了**（票面给的
   两条路里选「去掉」，不是「给提示」）。做法不是把上限调大，而是**换一条取数路**：右详情改打
   `GET /api/history/runs/{id}/steps`——一条运行的**消息步索引**（`id / runId / messageId / step /
   actionName / status / error / createdAt / attempt / businessKey` + 「两个快照落没落」两个布尔），
   **两个 TEXT 快照列一个都不取**。
   一行从「几十 KB」压到「两百字节」，一条 720 步的运行（逐页扫 `runs/summary` 量出来的库里最大
   一条：240 条消息 × 3 步）整条索引 100 KB 上下、两次往返（一页 500）拿完，所以界面**永远显示
   完整的消息与步骤链**，`失败 N 步` 也就不可能撒谎（那是本票的验收项之一）。要看快照本身是另一条
   路：点开那一步再按 id 取整行（`/history/steps/{id}`），#132 的快照面板接那一头——「列表要宽、
   详情要深」这一刀就切在这里。
   为什么不做「按消息懒加载」：chips 上那句「失败 N 步」是**每条消息**的判决，拿不到整条运行的
   消息步就只能撒谎。索引接口的 `size` 上限比列表那侧宽十倍（1000 对 100）也是同一个理由：
   列表一行带快照，索引一行不带。
   两处旁证：`HistoryControllerTest`（契约：runId 走路径、默认一页 500、上限 1000、不被
   `/runs/{id}` 抢走）、`MessageHistoryMapperTest`（真 SQL：投影里没有快照列、空白快照算没落、
   按 id 升序、60 KB 快照不拖慢它、分页真的在分页——那一类切片默认**没有**分页拦截器，
   要 `@Import(MybatisPlusConfig.class)`，不然 `total` 恒为 0、断言是假绿）。
   顺带一提：`GET /api/history/steps?runId=` 那条路**不动**——它是检索面（跨运行、最新在上、
   整行带快照），两条路各自的口径写在各自的注释里。

    **同一票的第二处偏差**：票面要步骤链节点的可访问名称写「步骤号、动作、**名称**、状态」四样，
   而 `message_step` 只有 `action_name` 一列——原型那两格（`s.action` 与 `s.name`）在这个模型里
   是**同一个值**，硬凑第四格只会把动作名写两遍。所以可访问名称落成
   `步骤 3 · 动作 push-qc · 状态 FAILED · 输入快照 有 · 数据快照 无`：票面要的信息一样不少，
   只是「动作」与「名称」在这里合成了那一格。要拆开得先有「动作类型」这一列（不是本票范围）。

6. **计数与运行摘要合到一个只读聚合接口**，口径是**当前筛选集**（任务 / 状态 / 业务键，不含分页）。
   不在前端按行补拉 `/history/steps?runId=` 做 N+1。

7. **每步耗时单独一张后端票。** `ActionChainRunner` 的单步包裹处计时 → `message_step.duration_ms`
   （nullable、旧数据不回溯、失败步也记）。页面按「耗时可能为空」渲染（`—`），所以它推迟也不拖垮页面。
   **明确不接受**用相邻消息步 `createdAt` 差值近似：那是**步间隔**（含排队与开销），与**动作耗时**
   不是一回事，两个语义不同的数字长得一样是最坏的含糊（`CONTEXT.md` 两条术语已分开）。

8. **快照只做显示侧降级**：非 JSON 文本、空对象、超长不卡死，各给一句口径说明。**不碰 #127**
   （`data_snapshot` / `input_snapshot` 是 TEXT，超 64 KB 写不进历史、成功的动作反被判失败）——
   那是链路写库的可靠性 bug，绑进来会让本期的验收失焦。

9. **对照（与上一步）照抄原型口径**（原型自带「对照口径」注）：按**叶子路径**对齐两侧快照，
   `改` = 同名路径取值变了，`增` / `减` = 只出现在一侧；判等用 `JSON.stringify`，数组**按索引**对齐，
   空容器记一格；配 `同 / 改 / 增 / 减` 四个计数。**连弱处一起接受**：数组中间插入或删除会让后续下标
   全判成「改」——本期不发明 LCS / 键对齐的语义 diff。这是**叶子路径级**对照，不是语义级。

10. **有意偏离 DESIGN-HANDOFF 一处。** 那棵 JSON 树继续用 `vue-json-pretty`（依赖已有、`deep` 可控），
    搜索降级为「过滤 + 自动展开到命中路径」，放弃原型里的行内 `<mark>` 高亮——该库只有
    `deep` / `showLength` / `highlightSelectedNode`，做不了高亮也做不了 diff；对照块本来就是路径对齐的
    **表格**而非树，自绘。契约说「保留交互可供性」，这一处是明知故犯，记在这里而不是留在代码里。

11. **四态补齐并进验收**：列表加载中（占位而非空白）、空态分「无数据 / 筛选无结果」两种文案、
    接口错误可重试、重投进行中按钮 pending 且成功后**列表与详情同步刷新**（现有实现只刷了 runs 模式下
    的展开缓存，这是重构最容易丢的一处）。toast 用 `ElMessage`；原型那个自绘 toast 属于 chrome，不进生产。

12. **键盘只做 Esc 关弹窗**，不做键盘导航，也不把 a11y 增强列进验收项（ADR-0013 记过 #106 那类
    命中区域的坑，收益小于回归风险）。

13. **验收 = 一个真机脚本** `tools/ui/message-history-*.cjs`（Playwright `~1.59.1`，需 5173 + 8080）：
    双模与默认 FAILED、三档筛选与计数口径、运行→消息→步骤链、快照三种降级、对照 `同/改/增/减`、
    重投后原步 `REDELIVERED` 且列表与详情都刷新、2–3 档窄屏不横向溢出。九档视口矩阵走截图比对，
    不塞进这个脚本（那是 `keyboard-narrow-screen-106.cjs` 那种专门脚本的活）。

## 结果

- **会得到**：消息历史页与原型同构；「哪一步慢、哪一步把哪个字段改成了什么」这类问题在这一页上
  能直接回答（对照块就是映射步骤的实际证据）；计数与运行摘要一次查询拿到。
- **会失去**：旧页面那张宽表格「一屏看全字段」的能力；以及 `vue-json-pretty` 之外还得自己维护
  一棵搜索态与一个对照块。
- **风险**：①单步计时动了可靠性主链路（`ActionChainRunner`），所以它是独立票、可单独回滚；
  ②全高骨架改的是本页与 App 壳的接触面，窄屏最容易被踩（本期键盘只留 Esc，风险已收窄）；
  ③`--ok-ink` 是原型给 `--success-ink` 另起的名字——实现时**只用生产那一支**，别把它搬进来
  变成第二个同义令牌。
  ④**实现 #129 时实测到的既有问题**：控制台全局有 `body` 默认的 **8px 外边距**（`tokens.css` 的
  `body` 规则只写了字体与底色，没归零外边距），四个页面实测都是 `htmlScrollH=916 / innerH=900`——
  即**每个页面都多出一条 16px 的页面级滚动条**。全高控制台要成立，得在令牌层给 `body` 加
  `margin: 0`（1 行；代价是四个页面整体上移 8px、并去掉那条多余滚动条，需跑 `tools/ui` 全量真机
  复验）。**本票（#129）不动 App 壳**（决策 3），故只保证「不比别的页面多溢出」；
  **已定：并进 #137**（与九档截图比对、`tools/ui` 全量真机一起做；验收口径 = 四个页面基线一致、
  页面级滚动条消失、四页截图逐档对过）。
  ⑤**切片之间的过渡期**：#129 拆掉旧的两张表格时，**重投（决策 11）与消息步检索模式（决策 5）
  暂时从页面上消失**，要等 #135 / #136 落地才回来；这段时间里 ADR-0009 的「断点重投」只剩后端
  接口可用。**已定：先把 #136（消息步检索）与 #135（重投）提前做回来**，再回到 #130 / #131——
  过渡期因此只跨两票（#136、#135 都只被 #129 阻塞）。
  ⑥**#129 里运行侧那格业务键筛得不省**：实现是「先 `LIKE` 扫 `message_step` 拿 runId，再 `IN` 筛运行」，
  一条业务键命中很多运行时就是一个无界 `IN`。口径对、代价大；#130 做每运行摘要接口时应把这两步
  收成一次查询（或换成子查询）。
  **补记（#130 落地时）**：已收成一次查询——命中判据下推成子查询（运行列表用 `EXISTS`，
  计数那条用 `JOIN` 后 `GROUP BY`，一条 SQL 出三个数）。聚合接口
  `GET /api/history/runs/summary` 的四个计数（运行 / 消息 / 消息步 / 失败步）取的是**整个筛选集**、
  与分页无关（决策 6 原话「不含分页」），而**每运行摘要有页**：`page` / `size` 只决定摘要回哪一批运行。
  理由是实测：全量回一次在 runs=2682 的库上要 1 MB（业务键那一格占大半），换来的是没人看的数字；
  界面上用得到的只有当前这一页。命中的业务键也**只在筛了业务键时**才回。
  三条实现层面的坑，都是这一票踩出来的，留给下一个动这块的人：
  ①**三个计数必须与运行数同一组筛选**（含业务键）。第一版把业务键漏在计数之外，实测筛一个不存在的
  业务键会得到「运行 0 / 消息 5478」——一个筛选集里运行是 0 而消息不是 0。业务键这一格现在同时进
  运行查询、每页摘要与三个计数，三处**只有一个定义**（`matchingRuns`）。
  ②**业务键不做字面量转义**：消息步检索那一侧用的是 MyBatis-Plus `like()`（不转义），运行侧若
  单边转义，同一个业务键在两个模式里会筛出不同集合；要改就三条路（两处 SQL + 界面说明）一起改。
  ③**MyBatis-Plus 3.5.17 的 `apply(sql, 参数…)` 在这套配置里没绑上参数**（`apply("status = {0}",
  "SUCCESS")` 连 FAILED 的行一起返回，被 H2 真 SQL 测试抓住），所以业务键子查询按老办法内联模式串，
  值先过 `likeLiteral`（单引号与反斜杠翻倍）。升级 MyBatis-Plus 时可以回头收拾这一处。
  ⑦**页头的 ADR 文案与 RUNNING 的脉冲点是原型的真实拷贝**（DESIGN-HANDOFF 要求保留真实文案与
  状态可供性），#129 就带了——不是漏进骨架的装饰；审查把它当「超出票面」时以本条为准。
