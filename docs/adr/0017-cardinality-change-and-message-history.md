## 背景

产品现在**一条消息 = 一行 = 一张表**：源数据逐条流过链，每条消息在每个动作上记一行消息步。
「批量 / 数组型」接口接不了——一次请求发 1000 条、一份报文拆成头行与子行，都需要**基数变化**：
一条变多条（拆分）、多条变一条（合并）。

基数变化一旦发生，「消息历史怎么显示」立刻撞上四个今天没有答案的问题：

1. **分不出哪几条是一批。** 今天唯一的分组线索是 `message_id`，而同一批里每条数据的 `message_id`
   各不相同。运行期手里其实有个批号（`edge.batchMessageId`），但它只活在交换器属性里、**一个字节都没落库**；
   而且它的粒度是**一次运行一个**（水位分批那条路上，批号在进入循环之前打一次），粗到当不了批边界。
2. **一次请求的报文只有一份，却有 N 行消息步。** 每条都存整份 = 磁盘炸 + 必然撞上快照列容量；
   只存片段 = 整批发了什么散在 N 行里翻不出来。
3. **重投粒度会打架。** 断点重投是拿失败那一行的输入快照、从该动作往后重跑。合并那一步的输入就是**整批报文**，
   于是「重投这一条」实际会把整批发一遍；界面上 N 个按钮 = 整批发 N 遍。
4. **业务键的归属会含糊。** 拆分之后，一条业务记录变成头一行 + 子件 N 行，
   「这一行代表哪个业务实体」不再只有一个答案。

## 决策

1. **批次是「某一步上的分组」，不是消息的属性。**
   批次编号随「动作」变：同一条消息在动作 1 那一行、动作 3 那一行可以属不同批次。
   唯一限制是**同一个动作上一条消息只属于一个批次**（它在那一步只执行了一次）。
   批次因此落在**消息步那一行**上，不是落在消息上。

2. **批号每执行一次现生成，且每一位都记。**
   不按配置推导——否则改一次动作配置，历史里过去的分组会跟着被重新解释（过去的事实被现在改了）。
   批号在链上**继承到下一个基数变化动作为止**，转手时换号；每一行消息步都带当前批号（36 字节，
   与几十 KB 的快照比可忽略）。界面上只在这一步**换了号**的地方画批次标签，中间那些步骤不画。

3. **批号诞生在「基数变化动作」上**：拆分动作每执行一次一个、合并动作每执行一次一个；
   读库动作那个批号（今天的口径是**一次运行一个**，粗到当不了批边界）只作兜底、**不指望它分组**
   ——MQ 入口与任务输入这些链根本没有读库动作。批号的作用就是给出「这一段从哪开始」，
   于是链上的批次是一段一段的：读 →（拆：新号）→（合并：新号）→ 写。

4. **拆分与合并动作各自记一行消息步。** 不这么做，批次只能挂在「下一个记行的动作」上，
   而那一步与批次没有因果关系，是借来的位置。这一行的输入是父消息 / 整批，输出是子消息们 / 响应。
   拆分那一行**既要父消息标识也要批号**，两个字段各管一件事：`parent_message_id` 管谱系
   （从哪条消息拆出来的，与哪一次执行无关），批号管分组（跟谁分在同一段里）。
   一条父消息被拆两次时（例如重投之后又走一遍），两次的子消息父消息标识完全相同，只有批号分得开
   ——父消息标识**不能反推分组**，所以两个都不省。

5. **合并等齐一批再发，整批同成同败。** 合并点之前有个攒齐的屏障：要么全记成功、要么全记失败，
   不留「看着成功其实没发出去」的行。一批的边界 = **上游读取批读完那一刻**（绑上游读取批），
   不做条数阈值——「界面上的一批」要永远等于「一次真实的上游批次」，与水位推进、失败重读范围对齐。
   真要限制单次发送条数，调**读库那一步的批大小**，一处生效，不在合并这里再切一刀。
   **超时只当失败判据，不当发送触发**：等过头就是这批卡住了，记失败，不静默发半批；MVP 可以先不做
   （卡住就是卡住，任务挂在那里用户看得见）。

6. **一次请求的报文只存一份。** 那一批在合并动作上多一条**摘要行**：整份请求与整份响应都在它身上；
   同批每条消息在该动作上仍各记一行，只存自己那一片（自己的请求片段 + 响应里配给自己的部分 + 自己的错误）。
   摘要行同样是 `message_step` 的一行，`message_id` 用 `batch:<批号>` 这种特殊值（该列非空，
   且「运行 + 消息 + 步骤」要唯一），`step` 是合并动作的序号，批号那一格就是它的批号。

7. **合并那一步只做整批重发。** 界面文案写「重发这一批（N 条）」，一次点击 = 一次请求。
   绝不摆 N 个「重投这一条」的按钮——那会变成「点 N 次就把整批发 N 遍」。
   合并**之前**的步骤仍是干净的 1:1，逐条重投在那里照旧成立。

8. **快照装不下就当场失败，不写半截**（沿用 ADR-0015 决策 4 的口径，扩展到摘要行）。
   于是**一次合并的条数有上限**，超了就发不出去。**#127 是这件事的前置依赖**：
   把快照列改大之前，别指望这条链能跑到 1000 条。
   **补记（#141 落地后）**：承载报文的三列（`message_step.data_snapshot` / `message_step.input_snapshot` /
   `job_run.input_snapshot`）已从 `TEXT` 提到 **`MEDIUMTEXT`（16777215 字节 = 16 MB）**，
   迁移 `V6__snapshot_mediumtext.sql`（幂等、不把已经更宽的列改窄）。容量常量
   `MessageHistoryService.SNAPSHOT_LIMIT_BYTES` 与列宽同源，跟着它走。
   选 `MEDIUMTEXT` 而不是 `LONGTEXT`：真实报文在几百 KB 量级（A7BIG 实测 344 KB，约 48 倍余量），
   而单条语句还受服务端 `max_allowed_packet` 约束——4 GB 是个够不着的上限，只会让「一次合并能装多少条」
   这个界线说不清。这道闸的**行为**没变：仍然显式失败、不写半截，只是界线抬到了 16 MB。

9. **业务键不变，改的是它指向的那几行装什么。** 一条消息一个业务键，合并不改这条；
   合并只影响「按业务键查到的那几行里装了什么」（不再是整批报文，而是自己那一片）。
   拆分那边则是真问题：头行的键与子行的键**不是同一个层级的实体**，在定拆分动作的配置字段时解决。

10. **批次只出现在右详情，不进列表默认、不进网址、不进筛选。**
    **界面形状（2026-09-28 用一次性原型比过三个结构后拍板，见文末「原型的去向」）**：
    - 骨架沿用现在这条：**步骤链**在上、选中的那一步的消息 **chip** 在下。批号变了的那一步，
      **链节点上带一个小批徽标**（只标「这一步是一批」，不摊开成员）；点它展开/收起。
      「批次当框、先选批再看消息」那个方案被否——它把「看某一条消息的完整步骤」变成要多点一次。
    - 徽标展开后是**一个组头加一组 chip**：组头写「发送批 · 一次请求 N 条 · 失败 M 条」；
      同批每条 chip 带自己那一步的状态。**「重发这一批（N 条）」只长在合并那一档的组头上、且只在该批失败时铺**；
      合并之前那些步骤仍是逐条重投（决策 7）。
    - 某一步上这条消息**自己一组**时画成虚线框，写「单条 · 不是一批」——读库链、MQ 链、任务输入链
      永远不会出现批次，它们就该长这样，不给用户「这一批只有一条」的错觉。
    - **摘要行也有自己的一条 chip**（与消息 chip 并排，写「批次」+ 短号）：它没有对应的消息，
      不这么摆就没地方进得去（决策 6）。
    - 批号本身不给用户（每次现生成的随机串，他拿到也没处输）。「按批次筛」留到真有现场抱怨再加。

## 替代方案（被否）

- **不落批号，界面按「时间邻近 + 同步骤号」事后猜批**：批次边界是执行时才知道的事实，
  事后猜等于让历史页撒谎（同批跨秒跑完的、前后两批挨着的，都会猜错）。
- **建一张批次表做批次实体**：MVP 内是过度设计——批次不需要自己的状态机，它只是子消息的投影。
  但「永不建表」这个承诺也不给（现场真需要批次级重投时再谈）。
- **批号按配置推导**：改配置会重新解释过去的分组，见决策 2。
- **时间 / 条数窗口攒批**：那会让「一批」变成「碰巧在同一个时间窗里到的那些」，
  与上游读库批次脱钩；水位与重读范围会出现第二套边界。
- **超时冲刷半批**：会漏数据——落单那条超时发走后，本该与它同批的数据成了第二批。
- **每条消息都存整份请求报文**：1000 条就是 1000 份，磁盘与快照列容量都撑不住。
- **合并那一步逐条重投**：一次点击发整批，界面承诺与后端行为相反。

## 后果

- 消息历史多出批号一列与摘要行，索引接口要带上批号（右详情分组要用它）。
  右详情仍是「先选步骤、再看这一步的消息」那条老路：批次是**某一步上的分组**（决策 1），
  这个方向天然自洽；「先选批、再看消息」那种把批次当框的走法已被否（决策 10）。
- 合并动作之前，那批数据的中间步骤行会**晚一点才有**（要等整批攒齐），
  一条数据从进链到出现在历史里会有一段看不见的时间。
- 合并之前的数据被单独重投时，它自己形成只有一条的上游批，**这一批就齐了、立刻发**
  ——不会挂在那里等；这是决策 5 的直接结果，不是毛病。
- 拆分 / 合并动作开始记消息步之后，历史页会多出这两类动作的行（以前它们不记行）。
- `CONTEXT.md` 新增三个术语：父消息 / 子消息、批次、摘要行。

## 原型的去向

界面那三个方向（chip 按批分组 / 批次画在步骤链里 / 批次当框先选批）是 2026-09-28 用一支
**一次性原型**比出来的：`frontend/prototype/prototype-message-history-batch.html`，`?variant=A|B|C`
切换，数据按本文口径造（8 条 = 一个读取批 → 拆成 8 条 → 合并成一次请求整批失败 → 各写各的库）。
裁决是「A 当基线 + 把 B 的批徽标挪到链节点上」，已并入决策 10。
**该文件与那次自检的脚本已删**：本仓 `frontend/prototype/` 放的是**视觉契约**（外部设计工具导出、
有 ADR 指过来），一次性原型混进去会被后来的人当成设计稿。真要重看三个方案，按决策 10 那几条重画即可。

## #139 落地（批次身份）

决策 1–10 一个字没改，落地时补齐了本文没拍板的那几处细节：

- **批内序号从 `1` 起**（「这批里第几条」）。本文只说「元素顺序 / 攒批顺序」，没说基数；
  取 1 起是因为它是要给人看的序号，`0` 起会在界面上写成「第 0 条」。**只在拆分与合并时写**，
  读库产生的那些行留空（空不是 0）。
- **读取批的批号收到「一批一个」**：原先它在 `prepareRead` 里打一次（**一次运行一个**，粗到当不了
  批边界，决策 3 说的就是这一条），现在打在 `readBatch` 上——每读一批现生成一个，这一批的每条源行
  共用它。读库动作之前就失败（水位库连不上 / SQL 语法错）时用的那个**兜底占位批号**保留原样：
  它同时是失败步的占位消息标识（`edge.batchMessageId`），只作兜底、不指望它分组。
- **「读取批 / 发送批」按摘要行分**：库里没有「动作种类」这一格（`message_step` 只有 `action_name`），
  而摘要行本来就是合并那一档独有的（决策 6，`message_id` 是 `batch:<批号>`）——所以判据是
  「这一组里有没有摘要行」。于是这一票的组头只出现「读取批」那一档，与票面一致。
- **「重发这一批（N 条）」的判据先立着、按钮不等这一票**：判据（**发送批**且这一批有失败）落在纯模块
  `frontend/src/history/batch.ts` 里并有自测，但界面上不铺——合并动作是 #142，那一票再接按钮。
- **一条一组按「不是一批」画**（决策 10 的执行口径）：**批大小 1 的读库批**在库里确实带着批号
  （这一票给读库每批现生成一个），但它只有一条——组头点开与不点开一模一样，凭空多出一个「批」字，
  正是决策 10 要挡的那种错觉。所以判档看的是**这一组几条**：一条 = 虚线框「单条 · 不是一批」，
  两条以上才按「读取批 / 发送批」分档。要看「哪几条是一起读进来的」就把读库那一步的批大小调大。
- **重投沿下原步的批次戳**：断点续跑路由跳过了读库那一步，批号不会现生成——不沿的话重投出来的那几行
  `batch_id` 是空的，右详情会把一条本来在某批里的链画成「单条 · 不是一批」。与业务键同一个道理
  （`redeliver` 里一起投给 resume 入口）。
- **索引接口只带批号**：右详情按批分组只要 `batch_id`；`batch_seq` 与 `parent_message_id` 这一票的
  界面用不到，不进索引行（索引行贵在只有几十到两百字节那条口径不变）。
- **元素 → 已初始化消息抽成 `service/ElementMessageFactory.java`**（静态纯函数 module：消息标识 /
  业务键 / 父消息标识 / 批内序号 / 外层字段继承），策略（何时开容器、批尾提交水位、split 之前结算
  动作耗时、失败步挂占位标识、批号何时换）留在 `RouteGenerator`——抽的时候**行为零变化**，
  业务键提取也从 `MessageHistoryService` 搬到这里（它是「元素 → 消息」这一步算出来的）。

## #140 落地（拆分动作）

决策 1–10 一个字没改，落地时补齐了本文没拍板的那几处细节：

- **配置三格与「来源」的可空口径**（决策 9 说拆分那边由这一票自己拍板）：`sourceStep` **可空**——
  空 = 取**当前消息体**（票面那句「消息体 或 来源步骤 + 路径」的前一半），填了取 `context[sourceStep]`；
  `sourcePath` 可空——空 = 来源本身就得是那个数组；`elementKey` **必填**（头行与子行不是同一个层级的实体，
  子消息的业务键得有出处）；`keepParent` 缺省 `true`。元素键只认**纯名字段**（不放开 `lines.0.code`
  那种下标段）：下标段在来源路径上有 List 下标的额外含义，元素键只该是「元素里叫这个名字的字段」。
- **来源取不到就当场失败**：步骤被断点跳过、路径断了、取到的不是数组——三种都显式抛错，
  不静默拆出 0 条（那会让运行「成功」而一条数据都不落库）。
- **批号在拆分那一行上还是上游那个**：`recordSuccessStep` 排在换号**之前**——那一行的批号是
  「读库那一批」的号（拆分是那一段的最后一站），换手只发给子消息（决策 2 的「继承到下一个基数
  变化动作为止」）。MQ 入口这种本来没有批号的链，拆分那一行的批号就是空的。
- **拆分那一行两格都齐**（决策 4）：记它之前先把 `parent_message_id` 指向**它自己**的消息标识
  ——那个标识马上就要给子消息用（子消息的父消息标识要指向它），所以父消息标识写在属性上、
  批号仍留上游那个；记完再把当前消息标识撤掉（否则后面失败步会挂错消息）。
- **批内序号取 split 自己的迭代下标**（`Exchange.SPLIT_INDEX`，+1 成「第几条」），不按值回头查
  元素在数组里的位置：同一个元素在数组里出现两次时那种查法会给两条都算「第 1 条」（决策 2 的
  「元素顺序」要的是位置，不是值）。
- **`keepParent` 摊平的是父消息本身**：来源对象（`sourceStep` + `sourcePath` 取到的那个）才是父消息，
  不是数组里第一个元素——按「父消息的字段」摊，才不会让父消息没有的那些字段去借第一个元素的。
- **split 表达式不用 `body()`**：Camel 的 `split(body())` 遇到 **Map** 会按 entry 摊开，每条子消息
  拿到一个 `Map.Entry`（拆分这一步的消息体既可能是数组、也可能是装着数组的报文，头行分表正是后者）。
  改成按「来源步骤 + 路径」现解析那片数组——与记行那一步同一个解析，同一份配置同一个答案。
- **收尾按开过的层数退够**：一条链可能叠两层 split（读库分批那层 `loopDoWhile` + `split`，拆分动作
  那层）——「读 → 拆分 → 写库」正是两层。两个坑都踩过：① 每开一层要 `end()` 一次、且必须**由内到外**
  （先关拆分、再交水位、最后关循环），否则水位处理器被追加进内层、每行提交一次；② Camel 的 `end()`
  在**循环体内**只往外退一层（嵌套时第一次返回的是外层那个 split、不是 loop），只退一次会让
  `((LoopDefinition) current)` 炸 `ClassCastException`，路由根本建不起来。
- **拆分的 `sourceStep` 与 `FIELD_MAP.sourceStep` 同一批闸口**：`ChainConsistencyValidator` 抽出一处
  判据（`stepProblem`），写时 400 / `/validate` errors / 启用前拦截三处共用；`bodySourceStep` 的写时
  校验也用同一份判据（只是错误文案里的字段名不同）。
