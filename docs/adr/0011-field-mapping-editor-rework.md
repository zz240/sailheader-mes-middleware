# ADR-0011: 字段映射编辑器改版（每个目标字段一行 + 校验统一到后端一个只读接口）

## 状态

- **采纳**（2026-09-14，`/grill-with-docs` 决议 + 一次 wayfinder 图）
- 相关：ADR-0005（字段映射智能化方向）、`CONTEXT.md`、`docs/features/field-mapping/README.md`、
  `docs/flows/transform-flow.md`
- 取代：ADR-0005 的**编辑器形态**部分（三栏 + 多级表格 + 双树点选）；ADR-0005 的智能化方向、建议器能力、
  结构探测契约**不变**
- 实现：#98（母票）与 #99–#107（9 张子票，本次实现从 #99 骨架开始）

## 背景

实施工程师配字段映射要在「三栏 + 多级表格」里逐格填：选来源步骤、手打来源路径、填目标字段、选转换类型，
带参数的还要开弹窗。三个具体问题：

1. **来源字段只能手打。** 顶部「来源字段」下拉的加载函数（`loadSampleFields`）全仓库无人调用，
   所以下拉永远是空的，用户只能凭记忆敲路径，敲错了不报错。
2. **配错了要等任务跑起来才知道。** 后端有四种情况不报错但结果不对：来源路径不存在时目标字段整个消失；
   拼接里有一个片段取不到值时字段消失；日期解析失败时原值原样输出；枚举查不到键时结果是 null。
   任务仍然显示成功。
3. **层级映射看不出来。** 制品 → BOM 这种两级结构，表格上很难看出「来源数组的每个元素变成目标数组的一行」。

参照原件（`frontend/prototype/reference-field-mapping-studio.html`）证明了一件事：换成「每个目标字段一行」的
布局，**后端的数据格式可以一个字都不改**——它那棵只有 7 种节点的表达式结构，正好对应后端已有的 7 种转换类型。

## 决策

1. **编辑器形态**：每个目标字段一行，一行只放**一个转换加一个来源**，不做行内嵌套。
   数组映射占一行，下面展开子行，子行的目标字段写相对路径。
2. **存进数据库的格式一个字不改**：还是 `{mode? / expression? / rules[]}` 加 `FieldMappingRule` 的 11 个字段。
   一行就是一条规则，数组行就是 `iterate: 'FOR_EACH'` 加 `children`。新旧编辑器读写同一份数据，所以能共存。
3. **不做拖拽、不做命令面板。** 主要靠点击和键盘。依据：参照原件里的拖拽在它自己的文件里就是坏的
   （`dragPayload` 未声明而脚本是严格模式），没有可参考的实现，等于从零写。
4. **界面上不出现 `$` 符号**，符号只出现在编译产物里。对照表见下：

   | 内部符号 | 界面显示 |
   |---|---|
   | `$s_N`（N ≥ 1） | 动作 N · 动作名 |
   | `$s_0` / 无来源步骤 | 任务输入 |
   | `$root.x` | 外层 · 字段名 |
   | 数组内相对路径 | 字段名，分组标题写「数组元素内」 |
   | `$index` 加起始值 | 行号 · 从 N 起 |

   注意：「外层」不能叫「上一层」或「父级」——编译器里它始终指这份来源数据的顶层对象，
   直接引用父级数组元素在现在的编译规则下做不到（`docs/flows/transform-flow.md` P9）。
5. **判断对错全部交给后端一个只读接口**（草稿校验）：收编辑器里的草稿、目标字段清单、来源样例、
   链上更早的动作序号、默认来源步骤，返回 `{errors, warnings, 编译产物}`。它不写数据库。
   前端不复制任何一条校验规则，只保留「这一行填了目标字段没有、选了来源没有、必填的填了几个」这类本地事实。
   不能直接用现有 `/validate`：那个按 job id 校验**已经存进数据库**的配置，而编辑器里的还没保存。
   **前端只镜像两样东西，都不是「值对不对」**：
   - **形状**：数组映射行放的是数组路径，数组元素子行放的是相对路径，子行取外层表头字段是 `$root.` 前缀；
     三种填串了写出来就是一份自相矛盾的规则，后端只看规则本身合不合法，查不出来
     （`source-picker.ts` 的 `fillRowFromPick`）。
   - **哪里能用**：行号转换只在数组元素子行里有意义（顶层用会被 `FieldMappingConfig.validate` 拒），
     所以顶层行上这一项置灰并写明原因（`transforms.ts` 的 `TRANSFORM_HINTS`/禁用原因）。
     这属于「这一项在这里能不能用」的界面可用性，不是替后端判值。
   值对不对（枚举表覆没覆盖、必填填了没、类型配没配上）一律不判，等只读接口（#103）来做。
6. **三处来源写法在界面上就分开**（#101）：数组行的来源是**来源数组**的路径，数组元素子行的来源是
   **相对路径**，子行要取数组外层的表头字段则走**外层引用**——规则里存 `$root.<路径>`，编译器还原成
   `$s_<step>.<路径>`，界面显示成「外层 · 字段名」。三种东西填串了写出来的就是一份自相矛盾的规则，
   而后端校验查不出来（它只看规则本身合不合法），所以这条形状由前端守住。
   界面上「外层」这一项只在数组元素子行里给：普通行没有「外面那一层」。
7. **数组行可展开 / 收起**，界面上的分组标题固定写「数组元素内」（相对路径的语境），子行可以手工加
   （目标字段从空开始写相对路径）。
8. **这一轮不把建议器接到界面上。** 后端的 `MappingSuggester`、`/mapping-suggestions`、映射历史全部保留，
   映射历史仍然在保存动作时累计，只是界面上暂时没有地方看它（下一轮补界面）。
9. **明确不做值的试算**（不做「这条表达式在这份样例上算出什么值」）：这需要在受控边界里真的执行表达式，
   是另一件事。草稿校验里基于样例的检查只**查样例里的值**，不执行表达式。
10. **前端保住一条后端查不出的不变量**：编辑器产出的每条顶层规则**显式写上 `sourceStep`**。
    原因：`sourceStep = null` 在后端合法（被当成「任务输入」），所以漏写后端查不出来，只会静默从任务输入取值。
    反过来，**组内子规则不能带 `sourceStep`**（继承组节点），带了 `FieldMappingConfig.validate` 会拒。
11. **目标字段清单和来源样例只在编辑器打开时存在，不落库。** 目标清单来自写库动作那张表的连库探测
    （HTTP / MQ 做目标时没有结构可探测，靠手工导入清单或贴样例）；来源清单来自链上更早那个动作
    最近一次成功运行的输出快照。列表里点一个字段就填进当前行，不用再手打路径。
12. **行可以手工加，目标字段可以手输**（#102）。参照原件的行全部由目标字段清单生成，清单不全时配不完，
    而「探不出目标结构」是常态（写目标是 HTTP / MQ 时，见第 11 条）。所以界面上有「+ 字段映射」
    「+ 数组映射」，数组行下面有「+ 子字段」「+ 行号」；目标字段既能从清单里选（补全清单按这一行的
    形状给：普通行给标量字段、数组行给数组字段、子行给数组元素内的相对路径），也能直接手输一个
    清单里没有的路径（行上标「手写」）。每一行能**清除**——清的是这一行「值怎么取」，目标字段与
    数组行的子行都留着——清除后行里给出「撤销」，把那一份配回来（撤销状态只活在编辑器里，不进规则）。

## 结果

- **会失去**：常驻的右侧目标树、中间的多级映射表、ENUM 和 CONCAT 两个弹窗（改成在行里直接编辑）、
  建议面板（表格 + 分页 + 已采用标记）、命令面板、拖拽。
  「从目标清单里选一个，或者手输路径来建行」这个能力还在，只是形式变了。
- **多出一个后端只读接口**（ADR-0005 决策 1 的「配置期校验」落到了这一个接口上）。
- ADR-0005 决策 5 的验收标准「字段映射 80% 由系统自动填充」**不再作为验收锚**，
  改用以 UI 真实链路为准的口径：**免手工比例 =（自动填充/采纳且未经人工修改的必填目标字段数）÷（必填目标字段总数）**；
  **中位时长 = 打开编辑器 → 保存成功的墙钟时间**。ADR-0005 决策 1 里「界面侧提供内联推荐与一键自动填充」
  是一条**能力要求**——决策 8 只能理解成「这一轮不接界面」，不能理解成删掉这个能力。
