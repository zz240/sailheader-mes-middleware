# 测试规约

面向 `spike/`（后端：Java 21 · Spring Boot 3.4 · Camel 4.10，JUnit 5 + AssertJ，数据库用 H2）。前端没有单元测试框架：纯逻辑用 `frontend/src/**/*-checks.ts`（`node --experimental-strip-types` 直接跑），界面用 `tools/ui/*.cjs`（Playwright，见 `tools/ui/README.md`）。

跑测试：`pwsh -File tools/run-tests.ps1 <类名>`，全量留到收尾各跑一次。

## 一条硬标准

**读测试的人只读用例名和断言，就能判断这个改动对不对。** 做不到就是写法问题，先改写法，不要靠评审的人硬啃。

## 一个用例只验一件事

- 单个 `@Test` 方法不超过 20 行（含准备、执行、断言、空行）。超了先想是不是在验两件事。
- 一个方法里出现第二个「执行」段落，就拆成两个用例。
- 三个用例只有参数不同，用 `@ParameterizedTest`，不要复制三遍。

## 命名

- 类名：`<被测类>Test`，与被测类同包。
- 方法名：**英文、动词开头、说清场景和期望**。
  - 好：`blankSuccessFieldsAreOmittedFromMap`、`timeoutZeroIsRejected`
  - 差：`test1`、`shouldWork`、`testParse2`、`case3`
- 类级 javadoc 用中文，写三件事：**这个类为什么存在、钉住哪条口径、不覆盖什么（指向别处）**，并挂上票号 `#N`。

## 准备数据

- 简单输入直接用 `Map.of(...)` 或字面量，不要为了"看起来可读"再包一层。
- 准备工作超过 10 行，抽成私有 helper 或 builder。禁止在每个用例里手工 `new` 一整套对象图。
- 只写**与这个用例相关**的字段，其余走默认值。
- 准备代码里不写断言，也不要有条件分支。

## 断言

- 只断**可观察行为**：返回值、状态、错误码、抛出的异常类型与关键消息。
- 不断实现细节：私有字段、内部调用次数、日志文本、拼出来的 SQL。
- `verify(...)` 只能当辅助，不能当主断言；主断言必须是行为结果。
- 异常用 `assertThatThrownBy(...).isInstanceOf(...)`，不要 `try/catch` 加 `fail()`。
- 断言写具体期望值，不要用 `isNotNull()`、`isNotEmpty()` 糊过去。
- `assertThatCode(...).doesNotThrowAnyException()` 只证明"没抛异常"，不能代替结果断言。

## 时间与异步

- 禁止 `Thread.sleep`。要等就用 Awaitility，或注入可控的 `Clock`。
- 依赖当前时间的逻辑，把 `Clock` 作为构造参数传进去；测试里传 `Clock.fixed(...)`。
- 时区相关的断言必须显式指定时区，不依赖 JVM 默认时区（已踩过：时间列按任务时区解释，不按 JVM 时区）。

## 数据库

- 只用 H2，禁止连本地 MySQL。
- 每个用例自己准备数据；不共享可变状态，不依赖执行顺序。
- 需要 schema 的用例用独立初始化脚本，不要改动其它测试依赖的公共数据。
- 测试结束后不要求清理，但断言不能依赖"上一个用例留下的数据"。

## 必查的边界

新增或修改一个行为，至少覆盖这几类：

| 类别 | 例子 |
|---|---|
| 空值 | `null`、空字符串、空集合 |
| 边界 | 0、负数、超长、越界、最大最小值 |
| 异常分支 | 非法输入、下游失败、超时 |
| 幂等 | 同一请求重复调用 |
| 并发 | 涉及共享状态时才需要 |

确实不需要覆盖的，在 PR 里写一句为什么。

## 禁止清单

以下行为一律不合格，评审直接打回：

- 删测试、注释掉断言、加 `@Disabled` 只为了让 CI 变绿
- 放宽断言（把 `isEqualTo("E001")` 改成 `isNotNull()`）
- 改实现去迁就测试（测试是规格，不是实现快照）
- mock 掉被测试的对象本身（那样测的是 mock，不是代码）
- 一个测试类里塞多个不相关话题
- 用大段准备代码掩盖"这个用例其实没验什么"

## 交付前自检（agent 用）

提 PR 前逐条回答，答案写进 PR 描述：

1. 新增或修改了哪些用例？各覆盖哪个场景？
2. 有没有边界用例？没覆盖的说明原因。
3. 跑测试的命令和真实输出（贴结果，不写"已通过"）。
4. 有没有改动、跳过或删除既有测试？为什么？
5. 断言里有没有依赖实现细节的？如果有，为什么必须这样断？

## 人怎么审（省时间的顺序）

1. 只看用例名清单：

   ```bash
   git diff master...HEAD -- '*Test.java' | grep '^+.*void ' | sed 's/.*void //'
   ```

2. 看「新增用例数」与「改动行数」的比例，明显失衡就深入看。
3. 抽查两三个用例的**断言**，不看准备代码。
4. 只看 PR 里贴的测试输出，不自己重跑。
5. 不逐行读测试。读不懂就是写法问题，打回改写法——这是规约问题，不是评审的人不够努力。
